The site is fully static: GitHub Pages serves files and runs no code. A playground that type-checks a snippet against
the definitions would therefore have to run the Luau type checker in the browser, compiled to WebAssembly. This page
records what was tried and why there is no playground yet.

## The requirement: Luau's new type solver

The definitions need Luau's **new type solver** (`LuauSolverV2`). They use `keyof<>` and `index<>` type functions for
`CreateFrame` and `EventHandler<E>`, and derive structures as `Base & { ... }`. The old solver rejects the file with
"Code is too complex to typecheck". luau-lsp turns the new solver on with `--flag:LuauSolverV2=true` (see
[editor setup](/wow-forever-luau-types/start/editor-setup/)).

## What was tried

[@luau-rs/luau](https://github.com/luau-rs/luau) (MIT) is a reimplementation of Luau in Rust. It publishes a
WebAssembly build to npm with a browser `AnalysisWorker`: strict checking, definitions files, hover types and
autocomplete, all off the main thread. It looked like a complete answer.

Version 0.739.0 fails on the first step: loading `wow-forever.d.luau` reports "Code is too complex to typecheck".
The Rust crates do have the `LuauSolverV2` flag, but the JavaScript bindings provide no way to set any flag. The
published build therefore always runs the old solver.

<Aside type="note">
  This was found by a test that ran the same library over `tests/pass` and `tests/fail`. A future playground should ship
  with a test like it, so the site never runs a checker that disagrees with luau-lsp.
</Aside>

## What it would take

Any of these would make a static playground possible:

1. **@luau-rs/luau exposes flags.** If a later release lets JavaScript set `LuauSolverV2`, the playground needs a few
   hundred lines (CodeMirror, a worker, diagnostics as lint). It also has to pass the agreement test above.
2. **A custom WebAssembly build of luau-rs.** A small `wasm-bindgen` wrapper sets the flag and calls the analysis
   crate. That puts a Rust toolchain and a build step into this repository's CI. It is also unclear whether the
   reimplemented solver handles every construct the definitions use.
3. **Luau's own C++ analyser through Emscripten.** This is the code luau-lsp runs, so it is the most faithful option.
   It needs a C++ wrapper for the frontend and definitions loading, and a pinned Emscripten toolchain. It is the
   largest piece of work.

Until then, use luau-lsp in your editor. The [addon template](/wow-forever-luau-types/start/addon-template/) sets it
up, and the API reference on this site gives the same types to read and search.
